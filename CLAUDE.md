# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

pnpm workspace monorepo (`pnpm@12`, packages in `apps/*`) with two independent apps that share no code yet:

- `apps/web` — front-end. React 19 SPA built with Vite 8, TypeScript 7, linted with **oxlint**. Entry: `src/main.tsx` → `src/App.tsx`. Dev server on Vite's default port (5173).
- `apps/api` — back-end. Next.js 16 App Router app (`src/app/`), Tailwind CSS v4, linted with **ESLint 9** (`eslint-config-next`). Its only page so far is the stock `create-next-app` one. Dev server on port 3000. Path alias `@/*` → `src/*`.

Both apps are still at their scaffold state.

## Commands

Run from the repo root (scripts in the root `package.json` wrap `pnpm --filter`):

```bash
pnpm install
pnpm dev            # both apps in parallel
pnpm build          # build all apps
pnpm lint           # lint all apps
pnpm test           # run tests in every app that has a `test` script

pnpm web:dev | web:build | web:lint | web:test | web:preview
pnpm api:dev | api:build | api:lint | api:start

pnpm web <script>   # run any script in apps/web, e.g. `pnpm web add <pkg>`
pnpm api <script>   # same for apps/api
```

Single test file or test name in the web app (Vitest):

```bash
pnpm web test src/components/atoms/Button/Button.test.tsx
pnpm web test -t "calls onClick"
pnpm web test:watch
```

`web:build` runs `tsc -b` before `vite build`, so it is also the type-check for the web app (test files are type-checked too). The api app type-checks during `next build`.

Native/postinstall builds are allow-listed in `pnpm-workspace.yaml` (`allowBuilds`: sharp, unrs-resolver, esbuild); add new entries there if a dependency needs a build step.

## Front-end (apps/web)

### Atomic Design

Components live in `src/components/`, one folder per level. A component may only import from its own level or lower:

| Level | Folder | What goes there |
|---|---|---|
| Atoms | `atoms/` | Smallest UI pieces with no other components inside: `Button`, `Input`, `Label`, `Icon`, `Avatar` |
| Molecules | `molecules/` | Small groups of atoms that do one job: `SearchField` (Input + Button), `FormField` (Label + Input + error) |
| Organisms | `organisms/` | Self-contained sections made of molecules/atoms: `Header`, `PostCard`, `CommentList` |
| Templates | `templates/` | Page layouts with slots (`children`/props); no data fetching |
| Pages | `src/pages/` | Fill a template with real data; the only level that fetches data or talks to the API |

Each component gets its own folder: `src/components/atoms/Button/{Button.tsx,Button.test.tsx,index.ts}`. Atoms, molecules and organisms receive data through props and stay free of API calls, so they can be tested in isolation.

### Tailwind

Style with Tailwind utility classes only. Don't add `.css` files or CSS modules for components. Tailwind v4 runs through the `@tailwindcss/vite` plugin; design tokens go in `src/index.css` under `@theme` (CSS-first config, no `tailwind.config` file). Components with visual variants map the variant to a class string (see `atoms/Button/Button.tsx`) and accept a `className` that is appended last.

### Component tests

Every component must ship with a colocated `*.test.tsx` covering its essential use: it renders with its required props, its main interaction works (click, typing, submit calls the right callback), and each variant/state that changes behavior (disabled, error, empty) is checked. Query elements by role, label or text, the way a user finds them, not by class names or test ids.

Stack: Vitest (configured in `vite.config.ts`, `jsdom` environment) + React Testing Library + `@testing-library/user-event` for interactions. `src/test/setup.ts` registers the `jest-dom` matchers and runs `cleanup` after each test. Import `describe`/`it`/`expect`/`vi` from `vitest` explicitly (globals are off). `atoms/Button/Button.test.tsx` is the reference example.

## Back-end (apps/api)

### Next.js 16 caveats

`apps/api/AGENTS.md` is generated by `next dev` and warns that this Next.js version has breaking changes relative to older training data. Before writing Next.js code, read the relevant guide in `apps/api/node_modules/next/dist/docs/` (Route Handlers: `01-app/03-api-reference/03-file-conventions/route.md`) and heed deprecation notices. Do not delete that block from `AGENTS.md`; `next dev` re-adds it.

`next.config.ts` enables `cacheComponents` and `partialPrefetching`, and wires Tailwind through Turbopack via `@tailwindcss/turbopack` (rule on `*.css`) instead of PostCSS. Tailwind is configured CSS-first in `src/app/globals.css`.

The API is built from Route Handlers: `src/app/<resource>/route.ts` for the collection and `src/app/<resource>/[id]/route.ts` for one item, exporting `GET`/`POST`/`PUT`/`PATCH`/`DELETE`. `params` is a Promise in this version (`const { id } = await ctx.params`); type the context with the global `RouteContext<'/resource/[id]'>` helper.

### REST rules

The API must follow REST principles:

- **Resources, not actions.** URLs name things with plural nouns (`/posts`, `/posts/42`, `/posts/42/comments`), never verbs (`/getPosts`, `/posts/42/delete`). Use kebab-case for multi-word paths. Nest at most one level.
- **HTTP methods carry the action** and keep their meaning: `GET` reads and never changes state; `POST` creates in a collection; `PUT` replaces a whole resource; `PATCH` updates part of it; `DELETE` removes it. `GET`, `PUT` and `DELETE` must be idempotent.
- **Correct status codes:**
  - `200` for a successful read or update that returns a body
  - `201` plus a `Location` header pointing to the new resource after `POST`
  - `204` with no body after `DELETE`, or after an update that returns nothing
  - `400` for malformed input, `422` when the input is well formed but fails validation
  - `401` when authentication is missing; `403` when the user is authenticated but not allowed
  - `404` when the resource doesn't exist, `405` when the resource exists but doesn't support the method
  - `409` for conflicts such as duplicates
  - `500` only for unexpected server errors

  Never return `200` with an error inside the body.
- **JSON in and out**, with `Content-Type: application/json`. Use one error body shape across every endpoint.
- **Collection queries use query parameters:** filtering (`?status=open`), sorting (`?sort=-createdAt`) and pagination (`?page=2&limit=20`). Don't use custom paths for them.
- **Stateless:** every request carries everything needed to handle it (auth goes in the `Authorization` header). Nothing about the client's session is kept on the server between requests.
- **Responses represent the resource** with consistent field naming (camelCase) and include the resource `id`.

## Git

Both apps use [Conventional Commits](https://www.conventionalcommits.org/):

```
<type>(<scope>): <description>

[optional body]

[optional footer(s)]
```

- **type:**
  - `feat` for a new feature, `fix` for a bug fix
  - `docs`, `style`, `refactor`, `perf`, `test`
  - `build`, `ci`, `chore`, `revert`
- **scope:** `web` or `api` for changes inside one app. Leave it out for repo-wide changes (root `package.json`, workspace config, this file).
- **description:** imperative mood, lowercase, no trailing period (`feat(web): add Button atom`).
- **Breaking changes:** add `!` after the type/scope (`feat(api)!: rename /users to /members`) and a `BREAKING CHANGE:` footer explaining the change.
- If one change touches both apps, prefer two commits, one per scope.
